# ADR-004: Build the Monday report in one pass, with no new index

- **Status:** Accepted
- **Date:** 2026-11-27
- **Decision owner:** Yaa Antwi

## Context

Adwoa's report takes about 40 minutes and sometimes does not finish. I never saw her actual query, so I rebuilt the way a report written one customer at a time would work, to see the shape of the cost. The brief does not say which orders count as spend, so I had to decide.

## Decision

Work out every customer's figures together, in one pass over the orders: total spent, order count, the last 12 months, a running total and a top 100. They are saved as views (saved questions that always show current numbers), and no index (a lookup shortcut) is added.

What counts as spend:

- Cancelled, canceled and refunded orders are left out. Capital letters and stray spaces in the status are ignored.
- Orders dated in the future, and orders whose customer is not on file, are left out.
- Pending and shipped orders count.
- The recorded order total is used, and the number of counted orders whose total disagrees with their items is shown, not hidden.
- Duplicate customers are flagged, not merged.
- A "notes" row shows what the report leaves out, so nobody trusts the figures blindly.

## Alternatives considered

### Alternative A: A bigger server

- **How it would work:** More power for the same slow report.
- **Why it is attractive:** No rewriting.
- **Why rejected:** The slowness comes from repeating the same lookups for every customer. The rebuilt slow way took about 4.1 seconds for just 20 customers, about 138 minutes if scaled to all 40,420. That scaling shows the shape of the cost, not Adwoa's real 40 minutes.

### Alternative B: Add an index

- **How it would work:** A lookup shortcut on orders by customer.
- **Why it is attractive:** It usually speeds up lookups.
- **Why rejected:** The report reads nearly every order, so the database did not use it and the time did not change. It also slowed 3,000 test sales from about 452 to 589 milliseconds (about 30%, in one run).

### Alternative C: A stored copy of the report

- **How it would work:** Save the results and refresh them on a schedule.
- **Why it is attractive:** Instant reading.
- **Why rejected:** It goes out of date, and the live version is fast enough.

### Alternative D: Count only completed orders as spend, or merge duplicates

- **How it would work:** A stricter meaning of spend, and fewer double-counted customers.
- **Why it is attractive:** Cleaner numbers.
- **Why rejected:** Pending and shipped orders are real money, and merging cannot be undone. Shared details do not prove it is the same person.

## Consequences

- **What this buys:** On your machine the all-customer summary took 0.19 to 0.28 seconds, the top 100 about 0.2 seconds, and the 12-month view with running totals about 1.0 second. It counted 140,015 orders worth 428,442,749.40 (no currency is named, because the data gives none).
- **What this costs:** The report is not "the" answer where totals disagree, so it must be read with its notes.
- **What it costs the client if I am wrong:** If pending orders should not count, spend is overstated. If duplicates are one person, a few rankings are split. Numbers stay wrong where the recorded total is wrong, until Nana says which is right.
- **What would make me revisit this:** The report taking more than a few seconds, or Nana or Adwoa confirming what each status means. **Who decides:** Nana or finance for the totals and statuses, and Adwoa for what her report must count.

## What this survives

Orders growing several times over. The report reads the orders once, so time should rise roughly in step with the number of orders. I did not test beyond today's 159,384 orders.
